MACaQ ported to MLX

MACaQ is a 4-bit weight quantization method that runs in its authors' llama.cpp fork. This report describes a port of its first step, the weight transform, to MLX, with GPTQ in place of its second step. The port was applied to Qwen3.5-0.8B-Base and Qwen3.5-9B and compared with the bf16 originals and with MLX's default 4-bit quantization of the same size.

2How the port works

2.1 What MACaQ does

MACaQ (huawei-csl/MACaQ, Apache-2.0; this port follows commit e9d4f89; paper arXiv:2611.10649) quantizes weights to 4 bits in two steps:

  1. Transform. For each linear layer, compute one scale per input channel, p = clamp(std(W)0.75 / rms(x)0.25, 10−4, 104), rounded to bf16. Divide the weight by p and multiply each block of 64 channels by a normalized Hadamard matrix. At run time the input is multiplied by p and transformed the same way, so the two cancel and the output is unchanged. After the transform, the few very large weights are spread over their block, and the 4-bit grid is no longer spent on them.
  2. Codebook quantization. Quantize the transformed weights to llama.cpp's IQ4_XS codebook using calibration text, followed by a vector-codebook refinement.

2.2 What was ported

MACaQ stepIn this portWhy
1　TransformPorted as is. Formula, exponent 0.75, block width 64 and Hadamard ordering are the same as in MACaQ's source.MLX has mx.hadamard_transform, whose ordering matches MACaQ's Sylvester matrix (the scripts check this on every run).
2　CodebookReplaced by GPTQ on the transformed weights, quantizing to standard MLX 4-bit (group 64).MLX has no IQ4_XS codebook format; porting it would need a new weight format and Metal kernels. GPTQ also uses calibration text to reduce the error.

2.3 Steps

A　Teach mlx-lm the transformed model macaq_mlx/qwen3_5_macaq.py

  1. Add a linear layer to mlx-lm's Qwen3.5 model that multiplies its input by p, applies the 64-wide Hadamard transform, then does the usual 4-bit matrix multiply.The model type is qwen3_5_macaq. import macaq_mlx registers it; alternatively, copy this one file into mlx-lm's models directory.

B　Transform macaq_mlx/port_convert.py

  1. Run the original on 128 chunks of calibration text (512 tokens each, public Wikipedia, Chinese and English) and record the RMS of every input channel of every linear layer.
  2. Compute p with MACaQ's formula, rounded to bf16, and transform the weights of the 186 linear layers with p and H.
  3. Test the transformed model before quantizing.Largest relative error against the original about 2×10⁻⁶; mean KL {{t_only}}; the homophone task picks the same word as the original on all items. The transform itself adds no error.

C　Quantize macaq_mlx/port_gptq.py

  1. Run the transformed model on all 261 chunks of calibration text and accumulate, for each linear layer, the Hessian of its transformed input (float32).mlx-lm's own GPTQ handles only plain linear layers and sees the input before the transform, so this step is written separately.
  2. Quantize the 186 linear layers to 4 bits with GPTQ, group 64, damping 0.01; otherwise as in mlx-lm 0.32.2's GPTQ.
  3. Quantize the embedding with plain 4-bit. Save standard MLX files; each transformed layer stores one extra vector p (about 1 MB in total).

B + C in one process macaq_mlx/port_layerwise.py

  1. Does steps 2 to 7 in one run, collecting Hessians for a group of decoder layers at a time with a checkpoint after each group. Used for the 9B (section 6.2).On the 0.8B its output is bit-identical to steps B and C run separately (all 880 tensors).

3Fidelity to the original (0.8B)

3.1 Method

  • Evaluation text: 100 chunks of 512 tokens from public Wikipedia articles (Chinese and English) not used for calibration. Only the second half of each chunk is scored, 25,600 tokens in all, as llama.cpp's perplexity tool does.
  • On every scored token, the original's and the quantized model's predictions give the KL, the perplexity, and whether the top-1 token is the same.
  • A homophone task of 233 items: one sentence, several candidate words with the same toneless pinyin; the model is right if it scores the correct word highest. This is how a small model is used to rank input-method candidates.
  • Script: scripts/eval_quality.py, on the Mac Studio. The same runs on the Mac mini agree to three decimals (KL 0.158 and 0.074).

4Public benchmarks (0.8B)

4.1 Method

  • lm-evaluation-harness 0.4.13, with the three variants loaded through mlx-lm's MLXLM wrapper. Zero-shot, no chat template (this is a base model).
  • Each question is scored by appending every answer option to the prompt and taking the option with the highest log-likelihood; the model does not generate freely.
  • Tasks: the English tasks most often reported for small models (MMLU, ARC, HellaSwag, PIQA, WinoGrande, BoolQ, LAMBADA, WikiText), plus Chinese ones (C-Eval, CMMLU, and the Chinese parts of XStoryCloze, XCOPA and XWinograd). 13 scored tasks, {{n08}} questions, plus WikiText perplexity.
  • Qwen does not publish scores for the 0.8B base model on these tasks, so the original's column was measured here, as a reference only.
  • CMMLU's Hugging Face dataset needs a loading script that recent datasets versions no longer run. Its official CSV release is used instead, with the same prompts as lm-eval's built-in cmmlu task (bench/lmeval/make_cmmlu_tasks.py).
  • Every question's result is kept (results/lmeval-0.8b/), so the variants are compared on discordant questions.

ReadingOn the English tasks, the port recovers part of what default 4-bit loses: about 40% on MMLU, half or more on ARC, HellaSwag and WinoGrande. On the Chinese knowledge tasks (C-Eval, CMMLU) and on LAMBADA both 4-bit variants lose the same, and the port recovers nothing. The three Chinese commonsense tasks (story ending, cause and effect, coreference) lose little to begin with.
BoolQ needs a separate lookOn BoolQ the port scores 1.7 points above the original. This is not better understanding. BoolQ is yes/no, and 62% of the correct answers are "yes". The original answers "yes" to 73% of the questions, default 4-bit to 68%, the port to 62%. Answering "yes" less often, the port gets more of the "no" questions right (69%, original 52%); on the "yes" questions it does the same as default 4-bit (81%, original 88%).

  • Speed was measured on the Mac mini M2 (16 GB), median of 5 runs in one sitting (scripts/bench_speed.py, results/qwen3.5-0.8b/speed-m2.json).
  • The slowdown comes from two small extra GPU operations per linear layer (scale and transform). Over 186 layers they add about 1.2 ms per generated token (6.8 ms → 8.0 ms).
  • The bf16 transform (p stored in bf16, scale and transform computed in bf16) leaves the quality practically unchanged on the 0.8B (KL 0.0743 against 0.0743, perplexity 18.18 against 18.18). It is selected with macaq.pre_dtype in the model's config (section 6.2) and is what the conversion scripts now write by default; the 0.8B measurements above use float32. Removing the overhead entirely would need a fused Metal kernel that does the transform and the 4-bit matrix multiply in one step.

6.2 Differences from the 0.8B port

Same two steps, same code, same calibration text: 128 chunks for the statistics, 261 for GPTQ, 512 tokens each. What differs:

Item0.8B9B
Transformed linear layers186 in 24 layers248 in 32 layers (24 linear-attention, 8 full-attention)
Output layerTied to the embeddingSeparate. MACaQ transforms only the decoder layers, so it gets plain GPTQ
MemoryOne passHessians for 8 layers at a time, 4 passes, a checkpoint after each (macaq-port). Weights stay unquantized until every pass is done, so each layer's Hessian still comes from the unquantized model, as in one pass
Time—32 minutes on the M3 Ultra, 33 GB memory peak
File425 MB5.04 GB, text only

Three changes were made for serving engines, and apply to both models:

  1. The port's layer no longer subclasses MLX's quantized linear layer. oMLX 0.7.2 replaces every QuantizedLinear with its own matrix multiply for prompts over 2048 tokens, which skipped the input transform and produced garbage on a 4,080-token prompt. With the change, oMLX and mlx-lm give token-identical output on short prompts and on the 4,080-token prompt. Parameter names are unchanged, so existing files still load.
  2. Config. architectures is set to Qwen3_5MacaqForCausalLM; otherwise oMLX loads the model as a vision-language model.
  3. Input transform in bf16. Casting the input to float32 for the transform makes long prompts need more transient memory (section 6.5), which made oMLX's memory guard pause requests. The loader reads macaq.pre_dtype from the config (float32, bfloat16 or float16; float32 when absent). Against float32, the bf16 transform on the 9B port gives KL {{klbf}}, perplexity 8.6683 → 8.6682, and the same pick on every homophone item.

  • Same setup as section 4: lm-evaluation-harness 0.4.13, the same 13 tasks, zero-shot, scored by option log-likelihood.
  • To finish in a day, only the first 40% of each task was used (for MMLU, C-Eval and CMMLU, the first 40% of each subject): {{n9}} questions, the same for all three variants. The fraction was set from the timing of a 2% trial run.

ReadingThe port is significantly better on 2 tasks, LAMBADA (discordant {{lam9}}) and C-Eval ({{cev9}}), and significantly worse on none. Over all questions it is right more often ({{pool9a}} against {{pool9b}}, p < 0.001). The perplexities agree with section 6.3: on WikiText default 4-bit is 6.4% above the original and the port 2.1%; on LAMBADA 13.6% against 2.4%. On the Chinese knowledge tasks, default 4-bit loses 3.2 points on C-Eval and the port 0.2; on CMMLU 2.3 against 1.5. On the English knowledge task MMLU, however, both lose about 2 points, and the port does not recover them. The 0.8B shows the opposite: MMLU partly recovered, C-Eval and CMMLU not.
CaveatsWith 13 separate comparisons, one p below 0.05 by chance would not be unusual. LAMBADA (p < 0.001) is backed by both perplexities and is the more reliable result; C-Eval rests on 47 discordant questions (p = 0.02) and should be read with care. XCOPA and XWinograd have about 200 questions each, so one question is 0.5 points; the port being 3.0 points above the original on XWinograd means nothing. On BoolQ the port again answers "yes" less often (58%, original 64%, default 4-bit 66%; 63% of the correct answers are "yes"), the same direction as on the 0.8B, but here the two 4-bit variants do not differ significantly.

7Limitations

  • Every evaluation was run once. The benchmark comparisons are question by question; differences of a few questions need the p value, not just the percentages.
  • The public benchmarks measure general ability with zero-shot, multiple-choice scoring and no chat template. The 9B results use the first 40% of each task, so single-task scores vary more than on full tasks. Neither model's scores should be compared with Qwen's published numbers.
  • MACaQ's second step (codebook refinement) is not ported. Its full pipeline in llama.cpp reaches KL about 0.034 on the 0.8B, half the port's 0.074, but at 498 MB (73 MB larger), and it runs only in MACaQ's llama.cpp fork.
  • There is no fused Metal kernel, so the port remains 10–15% slower in generation.
  • The 9B port is text only: the vision tower is dropped.
  • 9B speed was measured only on the M3 Ultra, not on a 16 GB machine.
  • The Mac Studio was shared with other jobs during the benchmarks, so their run times are not used as speed measurements.
  • Only two Qwen3.5 models were tested, with one version of MLX (0.32.4) and mlx-lm (0.32.2). Other architectures need their list of linear layers adapted.
  • The internal evaluations mentioned in section 0 used private data and are not reported.
